# [ST-007] Static IP for Kite orders: a Mumbai static-IP exit VM
[← index](../TECH_DEBT.md)

**Notes from ST-006 (2026-10-16):**
- SEBI's static-IP rule (enforced 2026-04-01) applies to Kite **order endpoints only**; Zerodha allows a primary and an
  optional secondary IP per developer account, shared by all its apps.
- rkneo50q's Tailscale address (100.x) cannot serve: it is private to the tailnet; Kite sees the home connection's public
  IP, which is dynamic (Airtel fibre; Airtel's box bridged, Rakesh's own router dials and holds the IP).
- A home static IP from Airtel was considered and **ruled out by Rakesh** (Airtel's static IP is unreliable).
- Tailscale's partner exit nodes (Mullvad) use shared IPs; Zerodha requires an IP used only by the account holder and
  immediate family, so they do not qualify.

**Design (Rakesh, 2026-10-27): a static-IP exit, not an order gateway.**
1. **Where:** AWS **Lightsail, Mumbai (ap-south-1)**, smallest plan with a public IPv4 (about Rs 400-500/month; confirm
   on AWS's pricing page). A Lightsail **static IP** attached to it (free while attached; it is the IP registered with
   Zerodha). Not chosen: Oracle Always Free (Oracle reclaims idle free instances, and a proxy is idle by their measure),
   GCP/Azure (more moving parts for a one-box job).
2. **What runs on it:** only a forward proxy (e.g. tinyproxy) listening **on the Tailscale interface only**, allowing
   CONNECT to `api.kite.trade:443` and nothing else. TLS runs end to end between rkneo50q and Kite: the VM never sees
   keys, tokens or orders. No stratrad code, secrets or database on the VM.
3. **stratrad side:** order calls only (ST-008/009) go through the proxy (`requests` proxy setting in `core/kite.py`);
   login, profile, holdings and margins stay direct. A failed order call through the proxy alerts and never retries
   blindly.
4. **Tailscale -- destination, never source:** the VM joins as tagged `tag:kite-exit` (not as Rakesh). ACLs: rkneo50q ->
   VM proxy port only; Rakesh's laptop/phone -> VM SSH only; VM -> nothing on the tailnet. ACL changes by the homelab
   project (owns the tailnet policy).
5. **Hardening:** Lightsail firewall blocks **all inbound** (Tailscale works outbound; SSH only over the tailnet);
   SSH keys only; automatic security updates; a short rebuild script + snapshot so a replacement box is ready in about
   15 minutes (the static IP is detached and re-attached, so Zerodha's registration does not change).
6. **AWS account (Rakesh):** MFA on the root login, a separate everyday IAM user, a billing alert (e.g. USD 10/month).
7. **Zerodha:** register the static IP as the **primary IP** in the Kite developer profile (IP whitelist); a secondary
   IP stays free for a later standby.
8. **Failure mode accepted:** if the VM is down, new orders wait until it is back; GTT stop-losses live at Zerodha and
   are unaffected.

**Static-IP check (prod, 2026-10-27):** first run FAIL -- through the proxy Kite saw the VM's **IPv6** address
(`2406:da1a:...`): the VM is dual-stack and api.kite.trade has AAAA records, so tinyproxy connected over IPv6. Fix: the
VM prefers IPv4 (`precedence ::ffff:0:0/96 100` in `/etc/gai.conf`; added to `setup.sh`, now 81 lines); `getent ahosts
api.kite.trade` -> 104.16.34.50 first. Second run **PASS**: through the proxy `HTTP 400 InputException: Invalid
`quantity`` (the order itself checked -> IP accepted; nothing traded); direct `HTTP 403 PermissionException: IP
(122.167.100.141) is not allowed to place orders for this app`.
**Lockdown 2026-10-27:** Rakesh's own laptop key (`id_ed25519_kiteexit`) added to the VM; SSH over the tailnet works
(`ubuntu@100.70.129.17`; the Lightsail default key was not used). Lightsail SSH rule deleted (IPv4 and IPv6) -- the VM
has **no** Lightsail firewall rule; from the internet 22/80/443/8888 on 13.205.57.58 all closed (Test-NetConnection
False x4). Inspection: no stratrad setting, key, token or database URL anywhere (grep over /etc /home /root /opt /srv: none;
the only .pem files are Ubuntu's public CA certificates); home holds only `setup.sh`; listeners = tinyproxy *:8888 (ufw:
tailscale0 only), sshd *:22 (ufw allows; no Lightsail rule, so tailnet only), systemd-resolved on 127.0.0.53/54,
tailscaled on the tailnet addresses; services = standard Ubuntu + tailscaled, tinyproxy, unattended-upgrades
(`amazon-ssm-agent` preinstalled: outbound only and inert without an IAM role, which Lightsail instances lack).
**Maintenance access:** (1) laptop `ssh kite-exit` (key `id_ed25519_kiteexit`, over Tailscale); (2) phone via an SSH app
with its own key (grant exists, not set up); (3) emergency: add a Lightsail SSH rule "Restrict to Lightsail browser SSH",
use the console, delete the rule after (needs the AWS login with MFA).
**Snapshot 2026-10-27** (Rakesh): Lightsail snapshot of `stratrad-kite-exit` taken after lockdown -- restore point

build a second VM from `setup.sh` with a fresh `tag:kite-exit` key, move the static IP, add the laptop key, re-run

**Steps and owners:** Rakesh -- AWS account (MFA, billing alert); Claude -- VM setup script, proxy config, stratrad proxy
setting, checks; homelab -- tailnet tag + ACLs, map entry; Rakesh -- register the IP with Zerodha.

**Done when:**
- From rkneo50q through the proxy, a request to `api.kite.trade` arrives from the static IP (Kite's IP check confirms
  the configured static IP is valid for the request's source).
- Through the proxy, any host other than `api.kite.trade` is refused.
- From the VM, connections to rkneo50q (PostgreSQL, SSH, Samba) and to Rakesh's other devices all fail (tailnet ACLs).
- From the internet, the VM has no open port (scan of its public IP finds nothing).
- Rebuilding from the script onto a fresh instance with the static IP re-attached works, timed.
- The VM holds no stratrad code, key, secret or token (inspected).
**Fail if:** the proxy forwards to any other host, the VM can open a connection into the tailnet, any inbound port is
open to the internet, or a Kite order endpoint is reachable from rkneo50q without the proxy's static IP being the source.
