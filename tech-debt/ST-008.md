# [ST-008] Guardrail service + guardrails.toml
[← index](../TECH_DEBT.md)

Design approved by Rakesh 2026-10-29, revised 2026-10-30 (limits become soft, subject to Rakesh's approval). See
"Design" and "Decided 2026-10-30" below; where they differ, 2026-10-30 wins.

**Decided inputs (Rakesh):**
- Limits so far: Rs 10,000 new buys/week; Rs 1,00,000 total at cost of open stratrad lots; Rs 40,000 per strategy;
  Rs 25,000 per sector; ~Rs 1,000 risk per trade (stop ~8-10% away); rolling 12-month loss tiers 10% alert / 15% no new
  buys / 20% halt.
- **Per-stock cap (2026-10-14): 8% of the overall capital cap** (Rs 8,000 at Rs 1,00,000), across all stratrad
  strategies. A setting in `guardrails.yaml`, not a hard number — may be raised if it proves too tight. Consequence at
  today's numbers: one lot per stock of <= Rs 8,000, risking ~Rs 640-800 at an 8-10% stop; >= 13 stocks at full cap.
- Caps count stratrad lots only; Rakesh's own holdings (strategy `manual`, docs/DATA_MODEL.md) never count.
- Guardrails run twice: before proposing and just before ordering (docs/DATA_MODEL.md section 5).
- From ST-003: genuine news-driven crashes happen (YESBANK -56%, INFIBEAM -71% in a day) — handle gap-downs through a
  stop, and consider news checks before buys.
- From ST-019 (2026-10-15): on a demerger ex-date the parent's price drops by the value spun off (MIRZAINT -86%,
  TATACHEM -57%), which is not a loss -- the holder receives the new shares. Guardrails and exits (the -15% rule, loss
  tiers, GTT stops via ST-009) must know upcoming demerger ex-dates and not fire on that gap; lot cost must be split
  between parent and new company (the factor from `config/demergers.csv`, or the official cost split).

## Design (approved 2026-10-29)

Three pieces, so the rules are testable without Kite or the database:

1. `config/guardrails.toml` — the enforced copy of the limits. Edited only by Rakesh; code and ML read it, never write it.
2. `execution/guardrails.py` — pure evaluator `evaluate(request, state, limits) -> Decision(allow|ask|block, rule_id, detail)`.
   No I/O, no Kite, no DB; every limit arrives as data.
3. `execution/guardrail_service.py` — gathers state, calls the evaluator, writes one `guardrail_events` row per check
   (stage, rule, decision, limits snapshot, context). The **only** module allowed in front of an order.

Called twice (docs/DATA_MODEL.md s.5): `before_proposal` (blocked -> logged, never shown to Rakesh) and
`before_order` (blocked -> proposal `blocked`).

**Fail-closed (Rakesh 2026-10-29):** any missing or stale input is a block, never an allow — missing sector, no
`daily_snapshots` row for the last trading day, panel or corporate actions past their fresh-by time, DB unreachable.
Each writes a `guardrail_events` row naming the missing input, so "no proposal today" is never ambiguous.

### Decided 2026-10-29 (Rakesh)
- **No max-position count** (the proposed G10 is dropped). The capital cap is the only size constraint and it is a
  revolving kitty: headroom = Rs 1,00,000 minus the **cost** of currently open stratrad lots. A GTT exit returns that
  lot's cost to headroom the same day. At ~zero headroom, no new buys until a lot exits or Rakesh allocates more.
- **Profits never re-enter the kitty.** A lot sold at a profit returns only its original cost; gains stay in the
  account. The buy kitty rises beyond Rs 1,00,000 only when Rakesh approves an increase (consistent with 2026-10-15:
  capital grows only when Rakesh allocates more).
- **Sectors (interim):** `stratrad_ro` gets SELECT on `portfolio_watch.stock_master` rather than a hand-refreshed
  snapshot. Needs a TD- issue on the MyInvestIQ side and a note to the homelab project (role change -> backup chain).
  Retired when Track F takes stock master over (ARCHITECTURE.md s.4). Check the real column names before querying.
- **CA blackout window:** 5 trading days before the ex-date.

### Decided 2026-10-30 (Rakesh)

**1. Limits are soft, subject to Rakesh's approval; validity rules stay hard.** "Rs 1 lakh isn't a hard limit"; then
"all limits are soft (subject to my approval)"; split approved as below.

| Rule | Kind | Outcome when breached |
|---|---|---|
| G03 kitty Rs 1,00,000 | limit | **ask** |
| G04 weekly Rs 10,000 | limit | **ask** |
| G05 lot Rs 12,000 | limit | **ask** |
| G06b entry-to-stop risk Rs 1,000 | limit | **ask** |
| G07 per strategy Rs 40,000 | limit | **ask** |
| G08 per sector Rs 25,000 | limit | **ask** |
| G09 per stock 8% of the cap | limit | **ask** |
| G11 alert / no-buys tiers | limit | **ask** (alert still only flags) |
| G12 CA blackout, 5 trading days | limit | **ask** |
| G11 **halt** tier (20% rolling loss) | the loss limit itself | **block** — lifted only by Rakesh editing the threshold in `guardrails.toml` (Claude's recommendation; Rakesh did not object — one word changes it) |
| G01 EQ series, Nifty 500, no SME/ASM/GSM, never `manual` | validity | **block** |
| G02 CNC, limit order only | validity | **block** |
| G06a stop present and below entry | validity — every lot gets a GTT | **block** |
| G13 stale or missing data | validity — the numbers being approved would be wrong | **block** |

Fail-closed is unchanged: a **missing** input (unknown sector, unknown open cost, no snapshot) is a block, never an
ask. A soft limit can only be asked about when the number is known and exceeds it.

**2. Committed money, not just open lots (Rule 1).** G03, G04, G07, G08 and G09 count open stratrad lots at cost **+**
approved proposals not yet filled **+** live entry orders not yet filled **+** (at `before_proposal`) proposals
already created earlier in the same run. At `before_order` the proposal being checked excludes itself. Rejected,
expired and blocked proposals count for nothing. Without this, picks in one run are each checked alone and the system
never notices a limit being crossed, so it could never ask. Worked example (kitty Rs 92,000; run proposes Rs 4,000 /
3,000 / 3,000): A and B go to Rakesh as normal, C goes marked "over the kitty by Rs 2,000 — approve?".

**3. How asking works.**
- One ask per lot, listing **every** soft breach (from `evaluate_all`), not one ask per rule.
- Each ask also shows the **running total of overage already approved**, so drift past the limits is visible even
  though no ceiling stops it (Rakesh: all soft; no ceiling set).
- Approving the proposal is approving its listed breaches; recorded in `audit_log` (actor `rakesh`, proposal, breaches,
  amounts). One-off for that lot — `guardrails.toml` is not changed; raising a limit permanently is still Rakesh
  editing the file.
- At `before_order` the breaches are recomputed. If they grew since approval (another fill landed in between), it asks
  again rather than using a stale approval.
- Until ST-011 (Telegram) exists nothing can approve, so an ask is unplaced in practice; the dry-run CLI shows ASK.
- `guardrail_events.decision` gains `ask` (migration 002).

**4. Sectors deviate from a settled decision, on purpose.** DATA_MODEL.md s.6 (2026-10-15) says research outputs the
live run needs, sectors included, are read from files (`reference/sectors.csv`, ST-005). The 2026-10-29 interim reads
them from `portfolio_watch.stock_master` over `stratrad_ro` instead. Only a **new** symbol's sector needs the lookup;
held lots already carry `positions.sector`. Rakesh 2026-10-30: proceed with the grant, and build ST-005's sectors file
when possible — it then replaces this read, the grant is revoked, and the deviation ends.

**5. Tier names follow the schema.** `daily_snapshots.tier` allows `ok / alert / no_buys / halt` (underscore). The
evaluator used `no-buys`, which would have been logged as an unrecognised tier (still a block, wrong reason). Fixed to
the schema's spelling.

### Decided 2026-11-06 (Rakesh) -- service layer

Sources, as built in `execution/guardrail_service.py`:

| Input | Source | If missing |
|---|---|---|
| Committed money, total and per stock / strategy / sector | open `positions` (not `manual`) at entry price x qty + unfilled part of live entry `orders` + approved `proposals` with no order + earlier picks of the same run | block |
| This week's buys (Mon-Sun IST) | lots entered this week + everything pending | block |
| Loss tier, snapshot present | latest `daily_snapshots` row, dated on or after the previous trading day | block |
| In Nifty 500, universe age | `universe/membership.csv`, review in force | block |
| Series | the price panel's last row for the symbol | block |
| Sector | `stock_master.our_sector` via `stratrad_ro` at `before_proposal`; the proposal's stored sector at `before_order` | block |
| Panel / corporate-action age | panel's last date; `max(corporate_actions.fetched_at)`; counted in trading days | block |

1. **Trading calendar:** MyInvestIQ's holiday archive, read-only (`CALENDAR_ARCHIVE_DIR`); an uncovered year makes an
   age unknown, so it blocks.
2. **G12 is fail-closed:** no source of announced FUTURE ex-dates exists (MyInvestIQ stores only past ones), so
   "unknown" blocks rather than meaning "none due". Lifted when stratrad's own corporate-action fetch keeps announced
   ex-dates. Until then every check blocks on G12 -- on top of G13, which already blocks on stale corporate actions.
3. **G01 surveillance (ASM/GSM) switch:** `instrument.surveillance_check = false` in `guardrails.toml` -- every check
   flagged `G01:surveillance-not-evaluated`. Turning it on (with a source of NSE's lists) is on the go-live checklist;
   on with no list read = block.
4. **G13 universe age:** the review in force must have taken effect within `freshness.universe_max_age_days` (214).
5. **G00 (before_order only):** the proposal must be `approved`; anything else blocks.
6. **Approvals:** an ASK becomes an ALLOW at `before_order` only when `approval_id` is an `audit_log` row (actor
   `rakesh`, action `guardrail_approval`, details from `approval_details()`) covering every current breach at no larger
   an overage. ST-011 writes that row; the format is fixed here.
7. **The falsifying clause is a test:** `tests/test_no_unguarded_orders.py` fails if any module naming a Kite order or
   GTT endpoint does not use the guardrail service. One reviewed exception: `scripts/kite_ip_check.py` (ST-007
   diagnostic; qty 0 at Rs 1, cannot execute).

Nothing writes `daily_snapshots` yet (ST-009), so on prod every check blocks on G13 until then -- by design.

### Scope boundary
ST-008 places no orders and moves no stops (ST-009), and sends nothing to Telegram (ST-011). It ships a dry-run CLI
that evaluates a hypothetical buy and shows ALLOW, ASK (with every breach) or BLOCK (with the hard rule).

**Done when:** every path that can reach a Kite order passes through `guardrail_service`, and each call writes one
`guardrail_events` row with stage, rule id, decision (allow / ask / block) and a limits snapshot. The dry-run CLI
evaluates a hypothetical buy and shows the outcome. Each soft limit is proven by a test that breaches exactly that
limit and asserts an ask naming it; each hard rule by a test that breaches exactly that rule and asserts a block naming
it. Committed money is proven by a test where three picks in one run each fit alone but not together, and the third
is asked about. Missing or stale sector, snapshot, panel or CA data blocks and names the missing input.

**Falsifying clause:** NOT done if any module outside `guardrail_service` can call a Kite order endpoint; or if a
`guardrail_events` row exists with `decision = 'allow'` whose limits snapshot shows a limit exceeded and which does not
reference an approval by Rakesh in `audit_log`; or if any hard rule can produce `ask` or `allow` when breached; or if
any test passes while `config/guardrails.toml` is absent.
