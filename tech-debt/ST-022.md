# [ST-022] Strategy research loop
[← index](../TECH_DEBT.md)

Raised by Rakesh 2026-10-29: "I would need some ability to adjust and retest candidate strategies."

ST-010 built the engine, the validator and the report cards -- enough to run a backtest. What is missing is the
discipline around repeated runs: which candidates exist, what was changed between runs and why, and what protects the
held-out years from being tuned against. Without it, adjusting a rule until the numbers improve is indistinguishable
from overfitting, and nobody can tell afterwards which it was.

Scope to be proposed before work starts.

## Evaluation decisions (Rakesh, 2026-10-29)

These were settled while reviewing the ST-010 backtests. They are recorded here, not in ST-010, because ST-010 is
Resolved and its file is a closed record (see the reference note at the end of tech-debt/ST-010.md).

1. **Test 1 keeps open lots at their own buy price.** Unrealised profit counts in neither direction -- it is not
   registered as gain while it builds, and giving it back is not registered as loss. This closes ST-010's last open
   card-change question ("does Test 1 need to see paper profits given back": answer no, keep as built). Only the
   faithful run's severity was affected; both limits runs pass either way.
2. **A strategy is considered on the full 2014-2026 span.** Development and inspection stay confined to
   2014-10-01..2023-12-31; the 2024-01-01..today slice stays sealed until a candidate is declared final, is then run
   once, and is reported separately with no changes afterwards (ST-010 decision 6 stands). The wider span is the BAR a
   candidate must clear, not a licence to tune across all of it -- tuning on the full span would make the reported
   numbers partly a description of the luck selected for, with no data left to catch it.
3. **`rakesh_top4, faithful` is a yardstick, not a candidate.** Rakesh already runs that rule himself, unconstrained;
   its role in the backtest was to show what the rule does without stratrad's limits. It never needed a verdict, and
   it is not a strategy stratrad would trade.
4. **Candidates are therefore two:** `rakesh_top4, limits` and `baseline_momentum`.

## Provisional reading on 2014-2023 (Claude; NOT a verdict)

| Run | Test 1 (worst 12m vs Rs 1 L stake) | Since start | CAGR | Nifty 500 = 12.8% |
|---|---|---|---|---|
| baseline_momentum, limits | -16.9% PASS | +Rs 27,477 | 2.0% | far behind |
| rakesh_top4, limits | -15.7% PASS | +Rs 1,34,927 | 8.4% | behind |
| rakesh_top4, faithful (yardstick) | -47.6% FAIL | +Rs 4,96,434 | 19.4% | ahead, but breaches the 20% loss limit |

On this evidence `rakesh_top4, limits` is the only plausible first live strategy, and `baseline_momentum` is a
plumbing baseline at best (964 lots in 9 years, charges above 2%/yr of capital, 2.0% CAGR). Per decision 2 neither
call is final until the held-out run exists.

**Blocked on:** the 2024-26 held-out run, which needs corporate actions after 2025-08-25 (a split would otherwise
read as a crash). That is Track F's daily corporate-action fetch (docs/ARCHITECTURE.md s.6), which recasts ST-020.

## Shape to propose (not yet agreed)

- A candidate registry: each candidate's rule file, its lineage (what it was derived from) and its state
  (exploring / final / rejected / live).
- A re-test log: one row per run of a candidate -- what changed since the previous run, why, who asked, the run_id in
  `data/backtests/`, and the headline numbers. Append-only; a count can lie, so the log must make the number of
  attempts visible.
- Hold-out enforcement: the engine refuses to run a candidate on the held-out window unless it is marked final, and
  marking it final is recorded. Looking at the held-out years and then adjusting the rule ends the hold-out -- that
  must be visible, not quiet.
- Where it lives: files alongside `data/backtests/`, or tables in the `stratrad` database. To be decided in the design.

**Open questions for the design:**
1. How many re-tests before a candidate is considered overfitted -- a hard number, a warning, or only a visible count?
2. Does a rejected candidate stay in the registry (so a later "new" idea can be recognised as one already tried)?
3. Does the held-out window move as time passes (2024-26 today; 2024-27 next year), and does moving it reset anything?

**Done when:** to be written when the design is agreed (observable behaviour + a falsifying clause).
